# 若依系统功能测试用例——优化思路与方法

> 版本：V2（优化版） ｜ 用例规模：49 条 → 83 条 ｜ 定位：资深测试工程师视角的用例集升级
> 配套产物：`docs/若依系统功能测试用例.xlsx`（16 列优化版）

---

## 一、为什么必须优化（原版 49 条的盲区盘点）

原版 49 条**覆盖了 8 个模块的增删改查主干**，作为第一版是合格的，但站在"项目级功能测试"的要求上，存在明显盲区：

| 盲区 | 原版缺失表现 | 风险 |
|---|---|---|
| 没有查询/筛选/分页用例 | 只有增删改，没有 list | 查询是每个模块的第一功能，且分页边界最容易出 bug |
| 没有状态管理用例 | 用户有启/停用，从未测过 | 状态机是业务核心，停用后能否登录是最典型缺陷 |
| 没有安全用例 | 未测注入/XSS/未授权访问 | 面试必问，上线必查，属于"没测就是风险" |
| 没有跨模块集成用例 | 模块各自为战 | 若依是 RBAC 系统，用户-角色-部门-权限的联动才是灵魂 |
| 没有审计用例 | 登录日志/操作日志是若依标准功能 | 审计能力是甲方验收必查项 |
| 缺少边界/异常输入 | 有少量边界，缺超长、类型错误、重复提交 | 边界值是最有效的缺陷发现手段之一 |
| 缺少业务规则分层 | 预期结果和"为什么"混在一起 | 不可追溯，评审/回归困难 |

**结论：第一版是"功能点列表"，优化版要成为"可执行、可追溯、可统计的测试资产"。**

## 二、优化总原则（资深工程师做用例的三个底层判断）

1. **先定"测什么"，再想"怎么测"**
   - 用例的价值 = 覆盖的风险；每条用例必须能回答"它在防什么 bug"。
   - 所以新增列 **业务规则/需求点**，让每条用例都能追溯到规则。

2. **用例要"可执行、可验证、可统计"**
   - 可执行：前置条件、测试数据写清楚，别人拿着就能跑。
   - 可验证：预期结果必须**可判真伪**（"提示 xxx" / "total=0" / "返回 code=500"），禁止写"应正常"。
   - 可统计：优先级分级 + 正逆向分类 → 支撑冒烟/回归/探索分层执行。

3. **测试数据是测试的一半**
   - 数据要**唯一**（自动化用 `{ts}` 时间戳）、**独立**（用例间不互相依赖）、**可清理**（后置清理，不留脏数据）。
   - 数据造不出来 → 用例就是废纸；所以每条用例的前置条件里都写明数据依赖。

| 字段 | 意图 | 对比原版 |

## 四、覆盖维度优化（49 → 83 条）

### 4.1 新增 5 个测试维度

```
查询与分页（5 条）     状态转换（用户启停 2 条并入用户管理）
安全与异常（5 条）     跨模块集成（4 条）
操作日志与审计（2 条）
```

### 4.2 各模块补充点

| 模块 | 原 49 条 | 优化后 | 新增了什么 |
|---|---|---|---|
| 登录认证 | 5 | 8 | 退出登录、验证码开关、连续失败策略确认 |
| 用户管理 | 9 | 15 | 密码长度边界、超长字段、SQL 注入、启停用状态机、重置密码 |
| 角色管理 | 7 | 9 | roleKey 重复、被用户占用的角色删除保护 |
| 部门管理 | 6 | 8 | 有子部门禁删、部门下有用户禁删 |
| 岗位管理 | 5 | 6 | 岗位编码重复 |
| 字典管理 | 7 | 9 | 字典数据键值重复、字典数据修改 |
| 参数设置 | 6 | 7 | 参数修改后全局即时生效 |
| 通知公告 | 4 | 5 | 公告类型边界值 |
| **新维度** | — | 16 | 查询分页 5 + 安全异常 5 + 跨模块 4 + 审计 2 |

### 4.3 特别值得讲的 3 个"资深视角"用例

1. **状态转换法（用户启停用）**
   - 不是两条孤立的"改状态成功"，而是组成闭环：`停用 → 登录失败 → 启用 → 登录成功`。
   - 状态机测试的核心：**每个状态迁移都要验证迁移后的行为**，而不是只看"状态字段变了"。

2. **删除保护类（部门/角色被引用不可删）**
   - 新手只测"能删"；资深工程师必测"**什么情况下不能删**"——这是数据完整性约束，是最容易漏的缺陷区。
   - 实测中若依确实对"有子部门/有用户"做了保护，这就是业务规则的证据。

3. **后端缺陷型用例（删除不存在 dict/config 返回 NPE）**
   - 这类用例的价值不仅是"发现 bug"，更是**给开发提缺陷单的依据**：`应返回友好提示而非 Java 堆栈`。
   - 简历里可以写："通过异常路径测试发现后端 2 处空指针缺陷"。

## 五、测试设计方法的应用矩阵

| 方法 | 本用例集中的应用 | 代表用例 |
|---|---|---|
| 等价类划分 | 有效类取 1 个代表值；无效类按"缺/重/错"拆 | 缺必填、名称重复、格式非法 |
| 边界值分析 | 取区间端点及邻值 | 密码 7/8/20/21 位、手机号 10/11/12 位、公告类型 1/2/3 |
| 场景法 | 主流程全链路（增-查-改-删）+ 异常流程 | 各模块"全链路"用例 |
| 状态转换法 | 状态迁移 + 迁移后行为验证 | 用户停用/启用闭环 |
| 错误推测 | 凭经验预测易错点 | 删除不存在 id、父部门不存在、重复提交 |
| 安全用例 | 注入/XSS/未授权/会话失效 | SQL 注入、XSS 转义、无 token 访问 |

**面试一句话版本**："我按等价类+边界值保证输入域覆盖，用场景法覆盖主流程与异常流程，用状态转换法覆盖状态变更类业务，用错误推测补充高危易错点，再用安全用例兜底注入与越权。"

## 六、测试数据管理策略（自动化项目已验证可行）

| 策略 | 落地方式 | 对应自动化实现 |
|---|---|---|
| 数据唯一性 | 命名带时间戳 `{ts}` | yaml/Excel 的 `{ts}` 渲染 |
| 数据独立性 | 每条用例自建自删，不依赖他人 | `cleanup_items` 后置 fixture |
| 数据可造 | 前置条件写明造数路径（API 或 UI） | probe 脚本先探契约再写用例 |
| 数据可清 | 每轮结束自动清理测试账号 | teardown 永远执行，失败只记日志 |
| 内置数据保护 | 逆向用例引用内置数据（如 sys_user_sex）只断言不删除 | 内置参数删除用例只验证"禁删" |

## 七、优先级与执行策略

```
P0（冒烟集）：登录、各模块增删改查主干、删除保护 → 每次发版必跑
P1（回归集）：状态管理、跨模块集成、必填/重复校验 → 每周回归
P2（探索集）：边界值、安全用例、异常输入 → 迭代期补充
```

执行顺序建议：**P0 冒烟 → P2 边界探索（找新 bug）→ P1 回归（验证修复）**，比一次性全量执行效率更高。

## 八、可追溯性设计（测试资产闭环）

```
业务规则/需求点 ←→ 功能测试用例（Excel） ←→ 自动化用例（ruoyi_Interface） ←→ 缺陷
      ↑                        ↑                        ↑                    ↑
  需求文档               "关联自动化用例"列           pytest 用例类名        "缺陷编号"列
```

- 每条 Excel 用例的**关联自动化用例**列直接指向 pytest 类/用例名，评审时一眼看出"这条有没有被自动化"。
- 执行失败 → 填**缺陷编号** → 缺陷修复 → 自动化用例补回归 → 闭环。

## 九、与自动化项目（ruoyi_Interface）的联动逻辑

```
功能测试用例（82 条，Excel）──定义"测什么"──┐
                                           ├─→ 自动化执行（39 条已落地）
probe 契约校准（实测返回）──保证"预期"真实──┘
```

- Excel 中标注了"实测"的预期结果（NPE 文案、操作失败、内置参数保护等）全部来自 probe 校准脚本，**不是拍脑袋**。
- 后续自动化扩展的选型依据就是这份 Excel：`关联自动化用例`为空的行 = 待自动化覆盖的缺口。
